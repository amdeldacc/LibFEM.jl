Candidate 1: Remove the unused type hierarchy

✦ Strong (emerald) Category: in-process

Files: src/types.jl, src/LibFEM.jl (include + 15 export lines), CONTEXT.md

Problem

types.jl exports 15 symbols:

  • 4 abstract types (AbstractElement{NDIM}, AbstractSpring{NDIM}, AbstractTruss{NDIM}, AbstractBeam{NDIM})
  • 3 concrete @kwdef structs (Spring{NDIM}, Truss{NDIM}, Beam{NDIM})
  • 8 type aliases (Spring1D … Beam3D)
  • 6 Base.show methods

No function in the codebase dispatches on any of these types.

"The abstract type hierarchy … and @kwdef concrete structs … are documentation-only scaffolding. They are NOT used by any element function, and there are no active plans to refactor functions to dispatch on them." — CONTEXT.md

The module is perfectly shallow. Its interface (15 exported names + 167 lines of documentation) is nearly as wide as its implementation. The deletion test: deleting types.jl concentrates zero complexity elsewhere.

Solution

  1. Delete src/types.jl
  2. Remove include("types.jl") from src/LibFEM.jl
  3. Remove all type/struct exports from src/LibFEM.jl
  4. Remove using Base: @kwdef
  5. Update CONTEXT.md
  6. No test changes

Wins

  • Locality: one fewer file; the naming convention tells the story
  • Interface shrinks: 15 exported symbols eliminated
  • Leverage: deletion is one change; every future reader has less noise
  • Honest code: what-you-see matches what-you-get

ADR conflict

CONTEXT.md (2026-07) explicitly decided to keep the type hierarchy. That decision was a tradeoff: ~120 lines for documentation value. The cost is now ~167 lines. The misleading cost — developers reading types.jl and assuming dispatch exists — outweighs the documentation value. Worth reopening the ADR.

Candidate 2: Deepen the 2D coordinate-based API

✦ Strong (emerald) Category: in-process

Files: src/truss.jl, src/spring.jl, src/beam.jl, src/utils.jl

Problem

All 2D element stiffness functions take angles in degrees (θ), but users must compute L and θ from coordinates at every call site:

L = d2_truss_elementlength(x1, y1, x2, y2)
θ = atan2d(y2 - y1, x2 - x1)
k = d2_truss_elementstiffness(E, A, L, θ)

The module is shallow: it pushes coordinate→angle transformation to every call site. Meanwhile, d3_spaceframe_elementstiffness already takes coordinates directly — creating an inconsistent seam.

Solution

Add coordinate-based overloads. No existing angle-based functions change.

function d2_truss_elementstiffness(E::Real, A::Real, x1::Real, y1::Real, x2::Real, y2::Real)
    L = d2_truss_elementlength(x1, y1, x2, y2)
    C, S = (x2 - x1) / L, (y2 - y1) / L
    validate_positive(A, "A")
    w = [C*C C*S; C*S S*S]
    return E * A / L * [w -w; -w w]
end

Same pattern for:

  • d2_truss_elementforces, d2_truss_elementstrain, d2_truss_elementstress
  • d2_spring_elementstiffness, d2_spring_elementforce
  • d2_planeframe_elementstiffness, d2_planeframe_elementforces

Wins

  • Locality: one call replaces 4 lines per call site
  • Leverage: N call sites, one deepened interface
  • Consistency: matches the d3_spaceframe coordinate-based pattern
  • Tests cover less boilerplate

Candidate 3: Generalize 3-node assembly

✦ Worth exploring (amber) Category: in-process

Files: src/assembly.jl, src/quadraticbar.jl

Problem

d1_quadraticbar_assemble does not delegate to the shared _assemble! helper. It has 9 individual indexed assignments, manual bounds checking, manual distinctness validation, and no @views. Every other element delegates to _assemble! with a one-liner.

Solution

Extend _assemble! to support N-node elements via varargs:

function _assemble!(K::AbstractMatrix, k::AbstractMatrix, ndofs::Integer, indices::Integer...)
    for (ri, rnode) in enumerate(indices)
        for (ci, cnode) in enumerate(indices)
            r_range = (rnode - 1) * ndofs + 1 : rnode * ndofs
            c_range = (cnode - 1) * ndofs + 1 : cnode * ndofs
            k_range = (ri - 1) * ndofs + 1 : ri * ndofs,
                      (ci - 1) * ndofs + 1 : ci * ndofs
            K[r_range, c_range] .+= @view k[k_range...]
        end
    end
    return K
end

Wins

  • Locality: one assembly code path for all elements
  • Leverage: adding future N-node elements is instant
  • Removes the comment explaining why quadraticbar is special
  • @views applies uniformly

Candidate 4: Delegate duplicated length functions

✦ Speculative (slate) Category: in-process

Files: src/truss.jl, src/beam.jl

Problem

FunctionDelegates?
d2_truss_elementlength— (primary)
d3_truss_elementlength— (primary)
d3_spaceframe_elementlength❌ identical to d3_truss
d2_planeframe_elementlength✓ calls d2_truss

d3_spaceframe_elementlength is identical to d3_truss_elementlength. The earlier pass handled d2_planeframe but missed the 3D version.

Solution

function d3_spaceframe_elementlength(x1, y1, z1, x2, y2, z2)
    return d3_truss_elementlength(x1, y1, z1, x2, y2, z2)
end

Wins

  • Locality: one implementation to check for correctness
  • Consistency: matches the d2_planeframe_elementlength delegation pattern

Top Recommendation

Remove the unused type hierarchy, then deepen the 2D coordinate-based API — in this order.

  1. Delete types.jl — pure simplification. No test changes. No downstream impact.
  2. Add coordinate-based overloads to d2_truss, d2_spring, d2_planeframe — completes the pattern that d3_spaceframe already follows.

These two changes together make the module depth match the expressed design intent: a function-oriented FEM library where the module absorbs coordinate transformation, and no dead abstractions confuse the structure.

The other candidates (N-node assembly generalization, elementlength delegation) are worth stacking in a follow-up but address smaller gaps.
